b:T2d6e,<p>LLM token cost is what you pay a model for the tokens it reads (input) and writes (output), each charged at its own rate per million tokens. This guide gives you the formula, prices one real-sized request on five models, explains why output, cached and reasoning tokens change the math, and shows which fields to read when the monthly AI bill does not add up.</p>
<p>All rates below are ATP list rates from each model page, as of October 2026. The vendor rates quoted for comparison link to the vendor&#39;s own pricing page.</p>
<h2 id="the-token-cost-formula">The token cost formula</h2>
<p>Every per-request cost on a token-priced API comes from the same three steps:</p>
<ol>
<li>Input cost = input tokens × input rate ÷ 1,000,000</li>
<li>Output cost = output tokens × output rate ÷ 1,000,000</li>
<li>Request cost = input cost + output cost</li>
</ol>
<p>On ATP Token, the request is then charged in credits against the <a class="doc-term" href="/docs/resources/" data-def="The unit that permissions and billing hang off — keys, allowed models, and credit budget all belong to one.">project</a>&#39;s balance, at <a href="/docs/credits/" class="doc-term-def" data-def="The billing unit. 1 USD = 100 credits; usage converts at each model's list rate.">1 credit = USD 0.01</a>. Credits = USD cost × 100.</p>
<h3 id="worked-example-one-support-bot-reply">Worked example: one support-bot reply</h3>
<p>A support bot sends a 1,284-token prompt (system prompt, retrieved help-center snippet, customer message) to claude-sonnet-4-6 at $3 input / $15 output per 1M tokens, and gets a 412-token answer.</p>
<ul>
<li>Input: 1,284 × $3 ÷ 1,000,000 = $0.003852</li>
<li>Output: 412 × $15 ÷ 1,000,000 = $0.00618</li>
<li>Total: $0.010032 = 1.0032 credits</li>
</ul>
<p>At 100,000 replies a month that is $1,003.20. Output is only 24% of the tokens in this request but 61.6% of its cost.</p>
<h3 id="a-token-cost-calculator-you-can-paste">A token cost calculator you can paste</h3>
<p>The SDK response already carries the token counts. With the OpenAI format the fields are <code>usage.prompt_tokens</code> and <code>usage.completion_tokens</code>; with the Anthropic format they are <code>usage.input_tokens</code> and <code>usage.output_tokens</code>.</p>
<pre><code class="language-python">RATES = {  # USD per 1M tokens: (input, output), ATP list rates
    &quot;gpt-5.5&quot;: (5.00, 30.00),
    &quot;claude-sonnet-4-6&quot;: (3.00, 15.00),
    &quot;gemini-3-5-flash&quot;: (1.50, 9.00),
    &quot;deepseek-v4-flash&quot;: (0.20, 0.40),
    &quot;qwen-3-7-flash&quot;: (0.03, 0.13),
}

def token_cost(model, input_tokens, output_tokens):
    rate_in, rate_out = RATES[model]
    usd = (input_tokens * rate_in + output_tokens * rate_out) / 1_000_000
    return usd, usd * 100  # (USD, ATP credits)

print(token_cost(&quot;claude-sonnet-4-6&quot;, 1284, 412))  # about (0.010032, 1.0032)
</code></pre>

<p>Two practical consequences. On a 5× or 6× model, trimming the answer is worth more per token than trimming the prompt: cutting 200 output tokens on claude-sonnet-4-6 saves $0.003, the same as cutting 1,000 input tokens. And workloads that generate long text (drafting, code generation, report writing) should be priced mainly from their expected output length.</p>
<h2 id="cached-input-and-reasoning-tokens">Cached input and reasoning tokens</h2>
<p>Two token types appear on vendor price sheets and confuse first-time readers.</p>
<h3 id="cached-input-is-a-vendor-pricing-feature">Cached input is a vendor pricing feature</h3>
<p>Some vendors price repeated prompt prefixes lower when they are served from cache. OpenAI lists GPT-5.5 cached input at $0.50 per 1M tokens against $5 for regular input (<a href="https://developers.openai.com/api/docs/pricing" target="_blank" rel="noopener noreferrer">OpenAI pricing</a>). Anthropic prices cache reads at 0.1× the base input rate on most models, with cache writes at 1.25× (5-minute) or 2× (1-hour) (<a href="https://platform.claude.com/docs/en/about-claude/pricing" target="_blank" rel="noopener noreferrer">Anthropic pricing</a>). These are vendor rates for calls made under those vendors&#39; caching rules. ATP Token bills on input and output tokens per its <a href="/docs/pricing-model/">pricing model</a>, so plan ATP budgets on the input and output list rates.</p>
<h3 id="reasoning-tokens-bill-as-output">Reasoning tokens bill as output</h3>
<p>Reasoning models think before they answer, and those hidden tokens count. OpenAI states reasoning tokens &quot;are billed as output tokens&quot; (<a href="https://developers.openai.com/api/docs/guides/reasoning" target="_blank" rel="noopener noreferrer">OpenAI reasoning guide</a>), and Anthropic bills extended-thinking tokens as output (<a href="https://code.claude.com/docs/en/costs" target="_blank" rel="noopener noreferrer">Claude Code costs</a>). If the support-bot request above used 1,500 thinking tokens on claude-sonnet-4-6, it would add 1,500 × $15 ÷ 1,000,000 = $0.0225, taking the request from $0.010032 to $0.032532, about 3.2×.</p>
<p>Reasoning budgets also explain a puzzling log line: a <code>200</code> with empty content. When <code>max_tokens</code> is too low, the model spends the whole budget thinking and returns no text. On ATP that request typically shows zero usage and deducts no credits; the fix is a higher <code>max_tokens</code> (<a href="/docs/errors/">errors</a>).</p>
<h2 id="what-a-per-request-record-tells-you">What a per-request record tells you</h2>
<p>A monthly total says how much. A per-request record says which project, which model and how many tokens. The record below is illustrative; it shows the fields you need to price one call, not ATP&#39;s literal log format.</p>
<pre><code class="language-json">{
  &quot;request_id&quot;: &quot;req_example_01&quot;,
  &quot;project&quot;: &quot;support-bot-prod&quot;,
  &quot;model&quot;: &quot;claude-sonnet-4-6&quot;,
  &quot;input_tokens&quot;: 1284,
  &quot;output_tokens&quot;: 412,
  &quot;cost_usd&quot;: 0.010032,
  &quot;cost_credits&quot;: 1.0032
}
</code></pre>
<p>In ATP Token the same information lives in three places:</p>
<ul>
<li>Request logs, one row per call: time, scope (workspace and project), model, endpoint, HTTP status, provider result, input and output tokens, billing status and request ID. Filter by time range, scope, model, status or request ID (<a href="/docs/monitoring/">Usage &amp; logs</a>). Retention is 7 days, so investigate a spike within the week.</li>
<li>Billing events, the line-item ledger shown in the console as a 90-day view, filterable by model, key, billing status or request ID (<a href="/docs/console-api-billing/">billing API</a>). Use this ledger as the billing source of truth.</li>
<li>The Usage page, which totals credits and tokens by model and by API key for a period.</li>
</ul>
<p>Every response also carries an <code>x-request-id</code> header, so an engineer can match one call in application logs to its row in the console.</p>
<h2 id="three-bill-anomalies-and-where-to-look">Three bill anomalies and where to look</h2>
<h3 id="spend-jumps-in-one-week">Spend jumps in one week</h3>
<p>Sort Usage by API key. If keys map one-to-one to projects, the jump lands on one owner immediately. Then filter request logs on that project and compare tokens per request before and after the jump. A rise from about 1,300 to 13,000 input tokens per call usually means someone started sending a whole document on every turn.</p>
<h3 id="the-rate-looks-right-but-the-total-does-not">The rate looks right but the total does not</h3>
<p>Check the model mix. Moving 20% of the 100,000 support replies from claude-sonnet-4-6 to gpt-5.5 raises that month from $1,003.20 to $1,178.16, with no change in traffic.</p>
<h3 id="requests-succeed-with-no-text">Requests succeed with no text</h3>
<p>Look for <code>200</code> rows with zero output tokens on a reasoning model. Raise <code>max_tokens</code> to cover thinking plus the answer.</p>
<h2 id="setting-this-up-in-atp-token">Setting this up in ATP Token</h2>
<ol>
<li>Create one project per service and environment, each with its own <code>atp-</code> key, so Usage by key reads as usage by owner.</li>
<li>Allocate credits to each project. The allocation is the project&#39;s ceiling; when its balance runs out, calls return <code>402</code> (<a href="/docs/cb-budget-caps/">budget caps recipe</a>). Projects can also turn on auto <a class="doc-term" href="/docs/topup/" data-def="Adding credits to the wallet. Minimum 5 USD, pay as you go.">top-up</a> with a trigger threshold and a monthly cap.</li>
<li>Log <code>usage</code> from every response with the model id, and run the calculator above per project each week.</li>
<li>Reconcile month-end against billing events, and use request logs for drill-downs inside the 7-day window.</li>
</ol>

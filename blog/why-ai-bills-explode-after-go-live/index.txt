<h2 id="a-post-launch-llm-cost-spike-worked-out">A post-launch LLM cost spike, worked out</h2>
<p>A support bot answers questions with retrieval-augmented generation on <a href="/models/claude-sonnet-4-6/">claude-sonnet-4-6</a>, ATP list rate $3 input and $15 output per million tokens as of October 2026. It handles 40,000 requests a day and writes about 400 output tokens per answer.</p>
<p>In the pilot, the average request carries 2,000 input tokens. After launch, users paste contracts and email threads into the chat, and retrieval adds more chunks to answer longer questions. Average input rises to 9,000 tokens.</p>

<p>The monthly delta is $25,200, a 2.75× bill. The model, its price, and the request count did not change. Nothing in a pricing table would have warned you. The only signal is average input tokens per request, which you see only if you record tokens per call.</p>
<h2 id="gap-1-shared-keys-leave-spend-without-an-owner">Gap 1: shared keys leave spend without an owner</h2>
<p>Symptom: The Usage page shows one key responsible for most of the month&#39;s tokens. Three services, a cron job, and a contractor&#39;s notebook all use it. When the contractor leaves, revoking the key would break production the same afternoon, so nobody does.</p>
<p>Why launch makes it worse: At pilot volume, sharing costs little. After launch, any one of those consumers can spike, and the only lever is turning the key off for everyone.</p>
<p>Fix: Make the project the unit of ownership, with one project per production system and its own key. A key belongs to exactly one project and inherits that project&#39;s allowed models and balance, and the API keys page lists every key across workspaces and projects (<a href="/docs/console-keys/" class="doc-term-def" data-def="A key that starts with atp-. It inherits its project's allowed models and credit balance.">managing API keys</a>). Revoking a key stops it immediately and keeps it in the roster for audit.</p>
<h2 id="gap-2-no-ceilings-so-the-invoice-is-the-alert">Gap 2: no ceilings, so the invoice is the alert</h2>
<p>Symptom: The staging job that ran all weekend. A retry loop sends 2 requests a second for 48 hours: 345,600 requests at 3,000 input and 300 output tokens on claude-sonnet-4-6. Each costs $0.009 + $0.0045 = $0.0135, so the weekend costs $4,665.60, found on Monday.</p>
<p>Why launch makes it worse: Batch jobs, agents, and retries run unattended. Without a ceiling per workload, one hot path draws on the whole organisation&#39;s balance.</p>
<p>Fix: Allocate credits down the tree (organisation, workspace, project) and treat each project&#39;s allocation as its cap. A project can only spend what it was given; when the balance runs out, requests return <code>402</code>. With a 50,000-credit ($500) allocation on staging, the same loop stops after about 37,000 requests, roughly 5 hours in. Steps: <a href="/docs/cb-budget-caps/">team with budget caps</a>. Allocated versus Consumed for every level is on the Usage page (<a href="/docs/credits/" class="doc-term-def" data-def="The billing unit. 1 USD = 100 credits; usage converts at each model's list rate.">how credits work</a>).</p>
<h2 id="gap-3-no-per-request-records-so-the-month-cannot-explain-itself">Gap 3: no per-request records, so the month cannot explain itself</h2>
<p>Symptom: Finance sees the bot go from $14,400 to $39,600. Engineering says nothing changed: same model, same price. The meeting ends without a cause.</p>
<p>Why launch makes it worse: Launch brings many changes at once: longer prompts, new retrieval settings, retry policy, more users. A monthly total cannot separate them.</p>
<p>Fix: Record project, key, model, status, and input/output tokens for every call. ATP Request logs show exactly these per request, filterable by time range, scope, model, status, and request ID (<a href="/docs/monitoring/">usage and logs</a>). In the example above, filtering Request logs to the bot&#39;s project shows rows carrying about 9,000 input tokens each. Set against the 2,000 recorded during the pilot, that answers the question in minutes, provided someone wrote the pilot number down. Track average input tokens per request per project as a weekly number.</p>
<h2 id="gap-4-no-model-allowlist-so-the-expensive-path-becomes-the-default">Gap 4: no model allowlist, so the expensive path becomes the default</h2>
<p>Symptom: Policy says a mid-tier model by default. Then a developer switches the bot to a stronger model to fix a tone complaint, and it ships.</p>
<p>Why launch makes it worse: Volume multiplies the price gap between models. The same post-launch traffic (40,000 requests a day, 9,000 input and 400 output tokens) costs very different amounts:</p>

Changing the bot&#39;s model then becomes a change to the project, made by an admin, instead of a one-line code edit.</p>
<h2 id="gap-5-no-review-cadence-so-problems-wait-for-the-invoice">Gap 5: no review cadence, so problems wait for the invoice</h2>
<p>Symptom: Nobody opens the Usage page between invoices. A cap raised for a one-off migration stays raised, and an unused key from a finished pilot stays active.</p>
<p>Why launch makes it worse: Controls checked once before launch drift afterwards: new keys, wider allowlists, larger allocations.</p>

<h2 id="close-the-five-gaps-in-five-working-days">Close the five gaps in five working days</h2>
<h3 id="day-1-monday-inventory">Day 1 (Monday): inventory</h3>
<p>Open the API keys page, which lists every key across workspaces and projects. For each key, write down which systems use it and who owns it. Mark every key used by more than one system.</p>
<h3 id="day-2-tuesday-split">Day 2 (Tuesday): split</h3>
<p>Create one project per production system and issue new keys. Move the highest-spend service first. Set a revocation date for each shared key.</p>
<h3 id="day-3-wednesday-allocate-ceilings">Day 3 (Wednesday): allocate ceilings</h3>
<p>Take each project&#39;s consumption for the last 30 days, add headroom for planned growth, and allocate that as the monthly ceiling. For the support bot after launch, that is at least 3,960,000 credits. Give staging and experiments small allocations.</p>
<h3 id="day-4-thursday-narrow-allowlists">Day 4 (Thursday): narrow allowlists</h3>
<p>Enable only the models each project needs. Call a disallowed model once from each project to confirm the <code>403</code>.</p>
<h3 id="day-5-friday-instrument-and-schedule">Day 5 (Friday): instrument and schedule</h3>
<p>Log the <code>x-request-id</code> header from every response next to your own feature or tenant ID. Put the weekly review on the calendar, and rehearse one key revocation end to end: revoke, check the logs, reissue.</p>

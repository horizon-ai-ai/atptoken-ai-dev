3:T2561,<p>LLM API 的密钥管理，是一套决定谁能拿到密钥、每个密钥能访问什么、存放在哪里、以及如何轮换与吊销的规则。在生产环境站得住的做法是一<a class="doc-term" href="/zh-cn/docs/resources/" data-def="权限与帐务的最小单位；密钥、允许模型、点数预算都挂在 项目 上。">项目</a>一密钥：每个工作负载有自己的项目，项目的密钥带着自己的模型清单与预算。下面依次整理共用密钥出问题的三种情况、发密钥的做法、各环境密钥存放位置的对照表，以及一份 30 天迁移流程。</p>
<h2 id="共用密钥出问题的三种情况">共用密钥出问题的三种情况</h2>
<h3 id="已离职的外包工程师">已离职的外包工程师</h3>
<p>一位外包工程师用公司唯一的一个 API 密钥做 RAG 原型，密钥放在本地的 <code>.env</code> 文件里，周五离职。同一个密钥还在跑客服机器人、每晚的摘要任务和内部的 Slack 助手。当天下午吊销它，三个服务一起挂；不吊销，等于一位已离职的外包手里还有一个能用的密钥。多数团队选择“下个 sprint 再轮换”，而下个 sprint 总是排满。</p>
<p>一项目一密钥的话，这位外包从头到尾只拿到自己沙箱项目的密钥。吊销它，其他什么都不受影响。</p>
<h3 id="被推到公开仓库的密钥">被推到公开仓库的密钥</h3>
<p>有人把含密钥的配置文件 commit 到公开仓库。拿到它的人发出的流量会算在你的账单上，而且因为每个服务都发同一个密钥，对方的请求在用量数据里和你的完全一样。处理方式与外包的情况相同，同样会带来一次停机。</p>
<h3 id="没人说得清的花费暴涨">没人说得清的花费暴涨</h3>
<p>月度账单翻倍。供应商的仪表盘看得出哪个模型用量上升，但每笔请求都带同一个密钥，没人能说清是哪个产品造成的。财务要求按产品拆账，工程师花两天比对各服务日志的时间戳。</p>
<h2 id="各家厂商的建议">各家厂商的建议</h2>
<p>OpenAI 的 <a href="https://help.openai.com/en/articles/5112595-best-practices-for-api-key-safety" target="_blank" rel="noopener noreferrer">API 密钥安全最佳实践</a> 要求每位团队成员使用各自的 API 密钥、定期轮换并设置过期，且永远不要把密钥放在客户端代码里。OpenAI 还建议把 staging 与生产环境分成不同项目，各自设置上限（<a href="https://developers.openai.com/api/docs/guides/production-best-practices" target="_blank" rel="noopener noreferrer">生产环境最佳实践</a>）。Anthropic 可以把 API 密钥限定在单个 Console <a href="https://platform.claude.com/docs/en/manage-claude/workspaces" target="_blank" rel="noopener noreferrer">工作区</a>。Vercel AI Gateway 的密钥可以同时设置预算与过期时间，适合有明确结束日期的外包密钥（<a href="https://vercel.com/docs/ai-gateway/observability-and-spend/budgets" target="_blank" rel="noopener noreferrer">Vercel 预算</a>）。</p>
<p>个人密钥解决的是人员离职的问题。生产服务不应该跑在某个人的密钥上，否则移除这个人，服务也会跟着停。实际可行的分法是：个人密钥给个人沙箱，每个已部署的工作负载各有一个项目密钥。</p>
<h2 id="发密钥的做法">发密钥的做法</h2>
<ol>
<li><strong>每个工作负载、每个环境各一个项目。</strong> <code>support-bot-prod</code> 与 <code>support-bot-staging</code> 是两个独立项目，各有各的密钥。</li>
<li>服务使用项目密钥，一个项目一个。需要做实验的人有自己的沙箱项目。</li>
<li>密钥按“服务、环境、签发月份”命名，例如 <code>support-bot-prod-2026-10</code>，在日志或仓库里发现时能直接对应到负责人。</li>
<li>密钥从控制台直接放进 secret manager，不要贴到聊天、工单或文档里。</li>
<li>用重叠方式轮换：在同一个项目发新密钥、部署、确认流量已经转移，再吊销旧的。</li>
</ol>

<h2 id="atp-token-的密钥如何工作">ATP Token 的密钥如何工作</h2>
<p>ATP Token 是四层结构：组织、工作区、项目、密钥（<a href="/zh-cn/docs/console-setup/" class="doc-term-def" data-def="账号的最上层，底下再分 工作区 与 项目。">设置组织</a>）。一个密钥只属于一个项目，并继承该项目允许的模型与<a class="doc-term" href="/zh-cn/docs/credits/" data-def="计费单位。1 点＝USD 0.01；用量依各模型牌价换算成点数扣抵。">点数</a>余额。模型权限按项目设置，从不按密钥设置，所以同一个项目里的两个密钥能调用的模型始终相同。</p>
<p>创建密钥的向导会让你填写名称、选择工作区与项目，并可选择先拨入一些起始点数。密钥以 <code>atp-</code> 开头、长度 92 个字符，完整密钥只在创建时显示一次，之后只能看到前缀（<a href="/zh-cn/docs/console-keys/" class="doc-term-def" data-def="以 atp- 开头的密钥，继承所属 项目 的允许模型清单与点数余额。">管理 API 密钥</a>）。API 密钥页面列出组织内所有工作区与项目的每一个密钥，可按名称或前缀搜索。吊销的密钥立即失效，并保留在列表中供审计。</p>
<p>追查花费时，用量页面按模型和密钥显示点数与 token，请求日志则记录每次调用的模型、状态、token 数与请求 ID（<a href="/zh-cn/docs/monitoring/">用量与日志</a>）。请求日志保留 7 天，事件发生后请尽快检查可疑的密钥。网关在转发请求前会去掉你的 <code>atp-</code> 密钥，上游供应商永远看不到它（<a href="/zh-cn/docs/how-it-works/">工作原理</a>）。</p>
<p>谁能做什么由角色决定：Admin 管理成员、资源、密钥与点数分配，Member 则使用自己有权限的内容（<a href="/zh-cn/docs/team/">团队与角色</a>）。</p>
<h2 id="迁移流程-从一个共用密钥到项目密钥">迁移流程：从一个共用密钥到项目密钥</h2>
<table>
<thead>
<tr>
<th>时间</th>
<th>步骤</th>
<th>完成标准</th>
</tr>
</thead>
<tbody><tr>
<td>第 1 天</td>
<td>在代码仓库、CI secrets 和 secret manager 中搜索共用密钥的前缀，列出每个调用方并指定负责人。</td>
<td>每个调用方旁边都有一个名字</td>
</tr>
<tr>
<td>第 2–3 天</td>
<td>每个调用方建一个项目，选定允许的模型、分配小额预算、发密钥。</td>
<td>每个项目的密钥都已放进 secret manager</td>
</tr>
<tr>
<td>第 4–10 天</td>
<td>先迁非生产环境：staging、CI、沙箱。在 ATP 上要改的是 base URL、<code>atp-</code> 密钥和模型 ID（<a href="/zh-cn/docs/cb-migrate-openai/">从 OpenAI 迁移</a>）。</td>
<td>非生产环境流量出现在新密钥下</td>
</tr>
<tr>
<td>第 11–20 天</td>
<td>生产服务一次迁一个，选低流量时段，每迁完一个就检查该密钥的用量。</td>
<td>每个服务的用量都出现在自己的密钥下</td>
</tr>
<tr>
<td>第 21–27 天</td>
<td>观察共用密钥。还有流量就说明有漏掉的调用方，找出来迁走。</td>
<td>共用密钥连续 7 天没有流量</td>
</tr>
<tr>
<td>第 28 天</td>
<td>吊销共用密钥。</td>
<td>已吊销，并记录原因与时间</td>
</tr>
<tr>
<td>第 30 天</td>
<td>写下泄露处理流程：吊销、在同一项目发新密钥、重新部署、检查该密钥的用量。</td>
<td>流程已放进值班手册</td>
</tr>
</tbody></table>

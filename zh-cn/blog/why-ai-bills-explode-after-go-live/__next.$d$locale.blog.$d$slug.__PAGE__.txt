3:T3f42,<p>企业 AI 账单失控，指的是大型语言模型或 AI 服务在正式上线后，用量费用在短时间内远超预算、且团队说不清「谁、哪个模型、哪一段变更」造成的超支。这份指南写给平台工程、财务与第一次要对 AI 费用签字的管理者。</p>
<p>先给答案：上线后账单爆炸，十之八九不是「原厂偷偷涨价」，而是<strong>五个控制缺口</strong>在 go-live 当下同时打开。缺口可以各自修，但真正有效的是同一套顺序——<strong>先让每一块钱有主人，再让每一个<a class="doc-term" href="/zh-cn/docs/resources" data-def="权限与帐务的最小单位；金钥、允许模型、点数预算都挂在 project 上。">项目</a>有天花板，最后让每一笔请求可回放</strong>。下面逐项对照症状、后果与修法；读完可直接当一周内的止血清单。若要先搞懂账单上的单位，可搭配<a href="/zh-cn/blog/how-to-read-your-ai-bill">怎么读懂 AI 账单</a>。</p>
<h2 id="为什么-go-live-是引爆点">为什么 go-live 是引爆点</h2>
<p>试用期的流量通常短、人少、上下文干净。上线后三件事同时发生：</p>
<ol>
<li><strong>真实上下文变长</strong>——用户贴整份文件、对话历史越堆越厚。  </li>
<li><strong>调用形态变复杂</strong>——agent、工具调用、失败重试，使「一次工作」变成「一连串请求」。  </li>
<li><strong>使用人数突然放大</strong>——从少数工程师变成整条业务线。</li>
</ol>
<p>单价表几乎没变，但「每次工作消耗的 token」与「谁能无上限调用」变了。没有控制层的系统，会把这三件事乘在一起，反映在同一张月底总额上。公开讨论里反复出现的失控叙事——没有用量上限、coding agent 人均成本失控、财务答不出是哪个团队——几乎都能对回下面五个缺口。</p>

<h2 id="缺口一-没有项目级密钥-费用没有主人">缺口一：没有项目级密钥——费用没有主人</h2>
<h3 id="症状">症状</h3>
<p>多个服务、脚本或个人工具共用一把 API 密钥；离职或换组时不敢轮换，因为「不知道还有谁在用」。</p>
<h3 id="为什么上线后会炸">为什么上线后会炸</h3>
<p>试用期流量小，共用密钥的隐性成本被掩盖。上线后任一子系统暴涨，你只能关掉整把密钥——等于关掉所有人——或眼睁睁看着总额爬升。</p>
<h3 id="修法">修法</h3>
<p>把治理单位定成<strong>项目</strong>，不是「人」：一个项目一把密钥，权限与预算挂在项目上。人离开时撤的是项目访问，不是公司共用的那把万能钥匙。密钥建立时只显示一次密文、之后可随时撤销并留审计轨迹——这是<a href="/zh-cn/docs/console-keys" class="doc-term-def" data-def="以 atp- 开头的金钥，继承所属 project 的允许模型清单与点数余额。">管理 API 密钥</a>的基本要求，也是<a href="/zh-cn/blog/ai-governance-checklist">企业 AI 治理清单</a>的第一项。</p>
<blockquote>
<p>共用密钥是治理里最贵的技术债：出事时你永远只知道「有人」，不知道「是谁」。</p>
</blockquote>
<h2 id="缺口二-没有预算上限-爆炸没有边界">缺口二：没有预算上限——爆炸没有边界</h2>
<h3 id="症状-2">症状</h3>
<p>供应商账户或信用卡「能刷就刷」；第一个正式信号是服务 402，或财务转来的异常发票。</p>
<h3 id="为什么上线后会炸-2">为什么上线后会炸</h3>
<p>Agent 与批处理可以在无人值守时连跑数小时。没有项目天花板时，单点异常会吃掉整份组织预算——这正是公开案例里「没设 usage limit」反复被点名的原因。</p>
<h3 id="修法-2">修法</h3>
<p>在<strong>项目层</strong>设可花的额度，把「分配下去的点数」当成 cap。组织 → 工作区 → 项目逐层下拨；项目只能花被分配到的量，超支应被标记并停止或降级，而不是静默透支到公司总账。操作顺序见<a href="/zh-cn/docs/cb-budget-caps">为团队设置预算上限</a>；点数在层级中的 Available / Allocated / Consumed 含义见<a href="/zh-cn/docs/credits" class="doc-term-def" data-def="计费单位。1 美元 = 100 点；用量依各模型牌价换算成点数扣抵。">点数如何运作</a>。</p>
<p>告警要早于切断：Usage 上能看到 Allocated 对 Consumed 的进度，才是「上线后还活着的预算」。细节见<a href="/zh-cn/docs/spend">追踪费用</a>。</p>
<h2 id="缺口三-没有逐请求归属-月报回答不了-为什么">缺口三：没有逐请求归属——月报回答不了「为什么」</h2>
<h3 id="症状-3">症状</h3>
<p>财务看到月总额上修 3 倍；工程说「我们没改价」；没有人能在一小时内指出是哪个模型、哪次部署。</p>
<h3 id="为什么上线后会炸-3">为什么上线后会炸</h3>
<p>上线后变更频繁——提示加长、换模型、重试策略、新 agent 步数。没有「一次请求」为最小单位的记录，你只能争论意见，不能排除假设。</p>
<h3 id="修法-3">修法</h3>
<p>每一笔调用写下至少：项目、密钥、模型、输入／输出 token、状态与时间。汇总才有意义；月总额是结果，不是分析起点。读法与角色分工见<a href="/zh-cn/blog/how-to-read-your-ai-bill">怎么读懂 AI 账单</a>；控制台的 Usage 与 Request logs 说明见<a href="/zh-cn/docs/monitoring">用量与记录</a>。</p>
<p>实用内部指标仍是<strong>每千次调用平均成本</strong>：它同时反映模型选择、提示长度与缓存策略，比盯着单价表更能解释「上线后为什么变贵」。</p>
<h2 id="缺口四-没有模型白名单-最贵路径成为默认">缺口四：没有模型白名单——最贵路径成为默认</h2>
<h3 id="症状-4">症状</h3>
<p>文件写着「默认用中阶模型」，实际日志里大量 frontier 模型；个人为了方便把 <code>model</code> 写死成当季最强。</p>
<h3 id="为什么上线后会炸-4">为什么上线后会炸</h3>
<p>上线后调用次数放大，模型单价差会从「几块钱实验」变成「预算主菜」。没有项目级允许清单时，切换模型是一行代码，不是一个需要理由的决策。</p>
<h3 id="修法-4">修法</h3>
<p>在项目设置<strong>允许的模型清单</strong>；不在清单内的请求在到达任何上游之前就被拒绝（例如 403）。<code>GET /v1/models</code> 是平台菜单，不是这把密钥的权限——这个区别写在<a href="/zh-cn/docs/models">模型文档</a>与<a href="/zh-cn/docs/how-it-works">系统如何运作</a>。白名单让「谁能用最贵模型」变成可回答的治理问题，而不是 code review 才能撞见的意外。</p>
<h2 id="缺口五-没有上线后监控节奏-问题活到月底">缺口五：没有上线后监控节奏——问题活到月底</h2>
<h3 id="症状-5">症状</h3>
<p>没有人每周打开用量；异常只在发票或客户投诉时浮现；Activity 里的权限与额度变更无人复核。</p>
<h3 id="为什么上线后会炸-5">为什么上线后会炸</h3>
<p>控制项若只在上线前检查一次，上线后的配置漂移（新 key、放宽白名单、调高 cap）不会被看见。治理是循环，不是启动仪式。</p>
<h3 id="修法-5">修法</h3>
<p>订一个轻量节奏：</p>
<table>
<thead>
<tr>
<th>节奏</th>
<th>看什么</th>
<th>谁负责</th>
</tr>
</thead>
<tbody><tr>
<td>每日（自动）</td>
<td>项目余额与错误率告警</td>
<td>平台／on-call</td>
</tr>
<tr>
<td>每周</td>
<td>按项目与模型排序的消耗；异常部署对照</td>
<td>平台 + 项目负责人</td>
</tr>
<tr>
<td>每月</td>
<td>点数对账、In debt 项目、无流量密钥</td>
<td>财务 + 平台</td>
</tr>
<tr>
<td>每季</td>
<td>权限清理、死亡项目、白名单瘦身</td>
<td>安全／内部审计对齐</td>
</tr>
</tbody></table>
<p>安全与管理事件（登录、邀请、额度变更）应与用量分开可查，见<a href="/zh-cn/docs/monitoring">用量与记录</a>的 Activity。完整 12 项循环见<a href="/zh-cn/blog/ai-governance-checklist">企业 AI 治理清单</a>。</p>
<h2 id="按团队规模-一周内先补哪几个缺口">按团队规模：一周内先补哪几个缺口</h2>
<h3 id="10-人以下">10 人以下</h3>
<p>先补<strong>缺口一、二、三</strong>：项目密钥、额度上限、看得到的请求记录。不需要委员会，三项都是设置。</p>
<h3 id="50-到-200-人">50 到 200 人</h3>
<p>加上<strong>缺口四</strong>：跨团队用量开始分叉，白名单决定「谁能用哪种模型」。同时把个人钱包与团队分配分开，避免业务线刷个人卡（见<a href="/zh-cn/docs/topup" class="doc-term-def" data-def="为钱包加值点数，最低 5 美元，用多少付多少。">储值与钱包</a>的 personal vs team 说明）。</p>
<h3 id="500-人以上">500 人以上</h3>
<p><strong>缺口五</strong>变成重心：上线只是起点，季度盘点与审计语言（逐请求可追溯）决定预算明年还在不在。组织层级从一开始就要长对，见<a href="/zh-cn/docs/console-setup" class="doc-term-def" data-def="帐号的最上层，底下再分 workspace 与 project。">设置组织</a>。</p>
<h2 id="按使用场景-哪种工作负载最容易引爆">按使用场景：哪种工作负载最容易引爆</h2>
<h3 id="coding-agent-与内部开发助手">Coding agent 与内部开发助手</h3>
<p>长上下文、多步工具、高重试——单位工作 token 远高于聊天。<strong>必须</strong>与生产服务拆开项目与额度；实验额度要低到「烧光也不痛」。接入方式可参考<a href="/zh-cn/docs/cb-claude-code">在 ATP 上跑 Claude Code</a>，重点是密钥与项目边界，不是工具品牌。</p>
<h3 id="客服与高频短请求">客服与高频短请求</h3>
<p>单次便宜，次数巨大。缺口在<strong>归属与模型分级</strong>：把高频路径锁在较小模型，frontier 留给升级路径。</p>
<h3 id="批处理与夜间-pipeline">批处理与夜间 pipeline</h3>
<p>无人值守放大缺口二与五。上线前就要有 cap 与告警；失败重试策略要有上限，否则 retry 本身就是一条隐藏成本线。</p>
<h3 id="多供应商同时导入">多供应商同时导入</h3>
<p>费率表与币种不一致时，若没有同一结算单位与项目归属，财务会先放弃。这是点数与单一账务窗口存在的理由，不是营销口号——见<a href="/zh-cn/docs/credits" class="doc-term-def" data-def="计费单位。1 美元 = 100 点；用量依各模型牌价换算成点数扣抵。">点数如何运作</a>。</p>
<h2 id="一周止血清单-可直接开票">一周止血清单（可直接开票）</h2>
<ol>
<li><strong>盘点</strong>：列出所有仍有效的 API 密钥、所属系统、是否共用。  </li>
<li><strong>切开</strong>：每个正式系统一项目一密钥；共用 key 排程退役。  </li>
<li><strong>盖帽</strong>：为每个项目写下月预算并做成可执行的额度（allocate）。  </li>
<li><strong>缩权</strong>：项目白名单只留需要的模型；默认不要 frontier。  </li>
<li><strong>开灯</strong>：打开逐请求记录与周会上的「按项目排序消耗」报表。  </li>
<li><strong>演练</strong>：假设密钥泄露——撤销、追 log、重发——写成一页 runbook。  </li>
<li><strong>对齐名词</strong>：让工程与财务共用 token／点数／项目三层语言（<a href="/zh-cn/blog/how-to-read-your-ai-bill">读懂 AI 账单</a>）。</li>
</ol>

<h2 id="更现代的做法-把五个缺口收成系统默认">更现代的做法：把五个缺口收成系统默认</h2>
<p>五个缺口都可以靠表格、供应商后台与人工纪律暂时堵住。更现代的做法，是让<strong>治理层与账务整合层</strong>在默认状态就关缺口：组织 → 工作区 → 项目的层级本身就回答「谁的预算」；项目密钥继承模型白名单与额度；余额耗尽以明确状态拒绝（例如 402），未授权模型在出站前拒绝（例如 403）；每笔请求写入可筛选的审计记录。</p>
<p>ATP Token 按这条路径设计：兼容 OpenAI、Anthropic 与 Gemini 的调用格式，接入通常是 base_url 与密钥；用量以点数在层级中下拨与归属。它不是用来取代模型供应商，而是在导入多家 AI 服务时，把权限、用量与账务收敛到同一平面。</p>

<h2 id="常见问题">常见问题</h2>
<h3 id="为什么-ai-服务上线后账单会突然暴涨">为什么 AI 服务上线后账单会突然暴涨？</h3>
<p>最常见的原因是 go-live 后用量形态改变——上下文变长、重试变多、agent 多步调用重送同一段上下文——同时又没有项目额度上限与逐请求归属。单价没变，总额却可以在几周内翻数倍。</p>
<h3 id="企业-ai-预算上限应该设在哪一层">企业 AI 预算上限应该设在哪一层？</h3>
<p>应该设在项目（或等同于项目的工作负载）这一层，而不是只设在全公司一张信用卡。项目层上限能隔离爆炸范围；公司总额只能告诉你「爆了」，说不出「哪里爆了」。</p>
<h3 id="共用一把-api-密钥为什么会让账单失控">共用一把 API 密钥为什么会让账单失控？</h3>
<p>共用密钥让每笔请求失去主人。出事时你只知道「有人」在烧钱，无法按项目停掉、限流或追溯。归账与止血都从「一项目一密钥」开始。</p>
<h3 id="没有治理平台能不能先堵住这些缺口">没有治理平台能不能先堵住这些缺口？</h3>
<p>可以。先用表格盘点密钥与项目、在供应商后台设额度告警、强制模型白名单、把请求日志导出到现有监控。平台的价值是把这些步骤变成默认值，而不是唯一做法。</p>
<h3 id="coding-agent-和一般聊天-api-的账单风险有何不同">coding agent 和一般聊天 API 的账单风险有何不同？</h3>
<p>Coding agent 常在长上下文、多轮工具调用与重试下运行，单位工作的 token 消耗远高于单次问答。若与生产服务共用密钥与额度，实验流量很容易把正式预算吃光。</p>

每張卡是一個缺口，以及 ATP 怎麼補上——不是再簽一家供應商。

01

金鑰散落

API 金鑰散落在個人帳號與共用文件裡，人員異動時難以盤點、更難收回。

ATP

金鑰只屬於專案。撤銷一次，全線失效。

02

帳單分散

每家供應商一張帳單、各自的幣別與週期，財務每個月都要重新對帳一次。

ATP

同一個點數錢包、同一張帳單，跨供應商收斂。

03

用量無法歸屬

只看得到總額，看不出是哪個部門、哪個專案、哪把金鑰產生的用量。

ATP

每筆請求記錄模型、金鑰、Token 與點數，歸到專案。

04

權限難以稽核

誰能呼叫哪個模型沒有單一事實來源，稽核時只能逐家供應商回查。

ATP

組織 → 工作區 → 專案階層，加上模型白名單。

Governance · 權限控管

誰能呼叫哪個模型，由結構決定。

以組織、工作區、專案三層階層界定每一把金鑰與每一個模型的範圍。權限跟著結構走，不跟著個人走。

  • 01
    三層階層

    組織、工作區、專案各自分層，成員角色與點數額度逐層分配。

  • 02
    模型白名單

    每個專案只能呼叫獲啟用的模型 ID，在流量抵達模型供應商之前就先把關。

  • 03
    金鑰範圍控管

    每把金鑰只屬於一個專案，權限、請求紀錄與點數消耗清楚隔離，隨時可以停用。

Billing · 用量與帳務

每一筆用量，都找得到主人。

所有供應商的用量都以逐請求的顆粒度記錄，收斂成同一份帳務視圖——單一帳務窗口，點數沿階層逐層分配。

  • 01
    逐請求歸帳

    每筆請求都記錄模型、金鑰、Token 用量與點數消耗，可歸屬到專案與部門。

  • 02
    點數分配

    點數由組織往下分配到工作區與專案，預算在事前就定好，不必事後追認。

  • 03
    單一帳務窗口

    跨供應商的費用收斂成同一份帳務紀錄，財務只需要面對一個窗口。

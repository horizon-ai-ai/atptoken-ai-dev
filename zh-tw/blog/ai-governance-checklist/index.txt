<h2 id="第一組-金鑰與身分-govern">第一組：金鑰與身分（Govern）</h2>
<h3 id="1-每把金鑰屬於一個專案-並有具名負責人">1. 每把金鑰屬於一個專案，並有具名負責人</h3>
<p>五個服務共用一把金鑰時，撤銷它就會讓五個服務一起停擺。每把金鑰只綁一個專案，做法見<a href="/zh-tw/blog/one-project-one-key/">一專案一金鑰</a>。</p>
<ul>
<li>完成標準：金鑰清冊中每把有效金鑰都列出專案與具名負責人，且沒有任何一把金鑰被多個服務使用。</li>
<li>負責人：平台團隊。</li>
<li>證據：金鑰清冊匯出，以及抽樣五個服務、顯示它們用的是五把不同的金鑰。</li>
</ul>
<h3 id="2-離職當天撤銷-ai-存取權限">2. 離職當天撤銷 AI 存取權限</h3>
<p>已離職外包人員的金鑰是最常見的缺口。把 AI 金鑰與主控台角色加進離職檢查表，和電子郵件、SSO 放在一起。</p>
<ul>
<li>完成標準：離職檢查表有一行處理 AI 金鑰與角色，且最近三位離職者都在一個工作天內處理完畢。</li>
<li>負責人：IT，由平台團隊執行金鑰撤銷。</li>
<li>證據：最近三位離職者的離職工單，附撤銷時間戳記。</li>
</ul>
<h3 id="3-沙盒與正式環境分開-沙盒有固定預算">3. 沙盒與正式環境分開，沙盒有固定預算</h3>
<p>實驗在獨立專案裡用獨立金鑰執行，預算小到失控的迴圈也不會變成月底驚嚇，例如每個團隊每月 50 美元。</p>
<ul>
<li>完成標準：沙盒金鑰碰不到正式環境的預算，且每個沙盒專案都有固定分配額。</li>
<li>負責人：工程主管。</li>
<li>證據：列出每個專案環境與預算的專案清單。</li>
</ul>
<h2 id="第二組-模型與資料邊界-map">第二組：模型與資料邊界（Map）</h2>
<h3 id="4-每個專案有模型白名單並記錄理由">4. 每個專案有模型白名單並記錄理由</h3>
<p>客服摘要專案可能只需要 <a href="/zh-tw/models/claude-haiku-4-5/">Claude Haiku 4.5</a>。要加入更貴的模型，應該開工單寫明理由；呼叫清單以外的模型則應該失敗。</p>
<ul>
<li>完成標準：每個專案都有明確的白名單，且對清單外模型的測試呼叫會回傳錯誤。</li>
<li>負責人：專案技術負責人，經平台團隊核准。</li>
<li>證據：各專案白名單匯出、變更工單，以及那次失敗的測試呼叫。</li>
</ul>
<h3 id="5-資料等級對應到允許的供應商與模型">5. 資料等級對應到允許的供應商與模型</h3>
<p>客戶資料能不能送進外部模型，不該由工程師每次自行判斷。一頁表格就能回答：資料等級、允許的供應商或模型、必要的前處理（例如遮罩）。</p>
<ul>
<li>完成標準：表格經核准並有版本，且每個專案都標註它會送出的最高資料等級。</li>
<li>負責人：資安或隱私團隊。</li>
<li>證據：附版本日期的簽核表格，以及專案對應資料等級的清單。</li>
</ul>
<h3 id="6-記錄每家供應商的資料條款">6. 記錄每家供應商的資料條款</h3>
<p>資料保留期間、是否用於訓練、處理地區，在不同供應商之間、同一家供應商的不同方案之間都不一樣。依供應商與方案逐一記錄，並附上你審查的條款版本連結。</p>
<ul>
<li>完成標準：每一家使用中的 AI 供應商與方案都在登記表上有一列，且在過去 12 個月內審查過。</li>
<li>負責人：法務或採購。</li>
<li>證據：附連結與審查日期的供應商登記表。</li>
</ul>
<h2 id="第三組-費用與歸屬-measure">第三組：費用與歸屬（Measure）</h2>
<h3 id="7-每個專案都有硬性花費上限">7. 每個專案都有硬性花費上限</h3>
<p>超支的第一個訊號，應該在帳單寄來之前就由上限觸發。指定一個人，在專案碰到上限時決定下一步：加值、等待，或改用較小的模型。</p>
<ul>
<li>完成標準：每個正式與沙盒專案都設定了上限，並有具名預算負責人。</li>
<li>負責人：各專案的預算負責人。</li>
<li>證據：上限設定，以及上一次有專案碰到上限時的處理紀錄。</li>
</ul>
<h3 id="8-每筆請求都能追溯-保留期配合稽核期間">8. 每筆請求都能追溯，保留期配合稽核期間</h3>
<p>任何一次呼叫，你都應該能說出它的專案、金鑰、模型、狀態與 token 數。確認你的工具把這些紀錄保留多久；如果比稽核人員抽樣的期間短，就定期匯出。</p>
<ul>
<li>完成標準：應用程式日誌中的請求 ID 能追到對應紀錄，且保留或匯出期間有書面記錄。</li>
<li>負責人：平台團隊。</li>
<li>證據：一筆從頭到尾追溯的請求，以及書面的保留期或匯出排程。</li>
</ul>
<h3 id="9-每月依專案對帳">9. 每月依專案對帳</h3>
<p>把各家供應商的用量換算成同一種單位，並把帳單總額與各專案用量加總對帳。各個項目怎麼讀，見<a href="/zh-tw/blog/how-to-read-your-ai-bill/">怎麼讀懂 AI 帳單</a>。</p>
<ul>
<li>完成標準：月報能把帳單對到各專案總額，超過約定門檻的差異都有書面說明。</li>
<li>負責人：財務，由平台團隊提供資料。</li>
<li>證據：最近三次的月對帳。</li>
</ul>
<h2 id="第四組-接入-事件與審查-manage">第四組：接入、事件與審查（Manage）</h2>
<h3 id="10-新-ai-服務只走一條接入流程">10. 新 AI 服務只走一條接入流程</h3>
<p>第 4 到 7 項要在發出第一把金鑰之前完成：白名單、資料等級、供應商條款、預算。費用報銷是交叉檢查，沒有接入工單的 AI 扣款就是 <a href="/zh-tw/blog/shadow-ai-governed-control-plane/">Shadow AI</a>。</p>
<ul>
<li>完成標準：本季新增的每一個 AI 服務都有接入工單，且費用報銷審查沒有發現缺工單的 AI 扣款。</li>
<li>負責人：平台團隊與採購。</li>
<li>證據：接入工單與費用報銷審查結果。</li>
</ul>
<h3 id="11-有金鑰外洩應變手冊且演練過">11. 有金鑰外洩應變手冊且演練過</h3>
<p>手冊列出撤銷、追查、重發的步驟，以及誰要通知誰。實際演練並計時。</p>
<ul>
<li>完成標準：手冊已發布，且過去 12 個月內演練過並記錄撤銷所需時間。</li>
<li>負責人：資安值班。</li>
<li>證據：手冊與附時間戳記的演練紀錄。</li>
</ul>
<h3 id="12-每季審查存取權限">12. 每季審查存取權限</h3>
<p>撤銷 30 天沒有流量的金鑰、關閉沒有負責人的專案、確認管理員名單。</p>
<ul>
<li>完成標準：在季末兩週內完成審查並簽核。</li>
<li>負責人：平台團隊。</li>
<li>證據：簽核過的審查紀錄，附撤銷的金鑰與角色變更清單。</li>
</ul>

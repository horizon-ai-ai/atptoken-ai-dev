25:T2517,<p>LLM API 的金鑰管理，是一套決定誰能拿到金鑰、每把金鑰能存取什麼、存在哪裡、以及怎麼輪替與撤銷的規則。在正式環境撐得住的做法是一<a class="doc-term" href="/zh-tw/docs/resources/" data-def="權限與帳務的最小單位；金鑰、允許模型、點數預算都掛在 專案 上。">專案</a>一金鑰：每個工作負載有自己的專案，專案的金鑰帶著自己的模型清單與預算。以下依序整理共用金鑰出事的三種情境、發金鑰的做法、各環境金鑰該放哪的對照表，以及一份 30 天遷移流程。</p>
<h2 id="共用金鑰出事的三種情境">共用金鑰出事的三種情境</h2>
<h3 id="已離職的外包工程師">已離職的外包工程師</h3>
<p>一位外包工程師用公司唯一的一把 API 金鑰做 RAG 原型，金鑰放在本機的 <code>.env</code> 檔案裡，週五離職。同一把金鑰也在跑客服機器人、每晚的摘要任務和內部的 Slack 助理。當天下午撤銷它，三個服務一起壞；不撤銷，等於一位已離職的外包手上還有一把能用的金鑰。多數團隊選擇「下個 sprint 再輪替」，而下個 sprint 總是排滿。</p>
<p>一專案一金鑰的話，這位外包從頭到尾只拿到自己沙盒專案的金鑰。撤銷它，其他什麼都不受影響。</p>
<h3 id="被推上公開-repo-的金鑰">被推上公開 repo 的金鑰</h3>
<p>有人把含金鑰的設定檔 commit 到公開 repo。撿到的人送出的流量會算在你的帳單上，而且因為每個服務都送同一把金鑰，對方的請求在用量資料裡跟你的完全一樣。處理方式跟外包的情境相同，同樣會帶來一次停機。</p>
<h3 id="沒人說得清的花費暴衝">沒人說得清的花費暴衝</h3>
<p>月帳單翻倍。供應商的儀表板看得出哪個模型用量上升，但每筆請求都帶同一把金鑰，沒人能說是哪個產品造成的。財務要按產品拆帳，工程師花兩天比對各服務日誌的時間戳。</p>
<h2 id="各家廠商的建議">各家廠商的建議</h2>
<p>OpenAI 的 <a href="https://help.openai.com/en/articles/5112595-best-practices-for-api-key-safety" target="_blank" rel="noopener noreferrer">API 金鑰安全最佳實務</a> 要求每位團隊成員使用各自的 API 金鑰、定期輪替並設定到期，且永遠不要把金鑰放在用戶端程式碼。OpenAI 也建議 staging 與正式環境分成不同專案，各自設定上限（<a href="https://developers.openai.com/api/docs/guides/production-best-practices" target="_blank" rel="noopener noreferrer">正式環境最佳實務</a>）。Anthropic 可以把 API 金鑰限定在單一 Console <a href="https://platform.claude.com/docs/en/manage-claude/workspaces" target="_blank" rel="noopener noreferrer">工作區</a>。Vercel AI Gateway 的金鑰可以同時設定預算與到期日，適合有明確結束日的外包金鑰（<a href="https://vercel.com/docs/ai-gateway/observability-and-spend/budgets" target="_blank" rel="noopener noreferrer">Vercel 預算</a>）。</p>
<p>個人金鑰解決的是人員離職的問題。正式服務不該跑在某個人的金鑰上，否則移除這個人，服務也跟著停。實際可行的分法是：個人金鑰給個人沙盒，每個部署中的工作負載各有一把專案金鑰。</p>
<h2 id="發金鑰的做法">發金鑰的做法</h2>
<ol>
<li><strong>每個工作負載、每個環境各一個專案。</strong> <code>support-bot-prod</code> 與 <code>support-bot-staging</code> 是兩個獨立專案，各有各的金鑰。</li>
<li>服務使用專案金鑰，一個專案一把。需要實驗的人有自己的沙盒專案。</li>
<li>金鑰以「服務、環境、發行月份」命名，例如 <code>support-bot-prod-2026-10</code>，在日誌或 repo 裡撿到時能直接對到負責人。</li>
<li>金鑰從主控台直接放進 secret manager，不要貼到聊天、工單或文件裡。</li>
<li>用重疊方式輪替：在同一個專案發新金鑰、部署、確認流量已經轉移，再撤銷舊的。</li>
</ol>

<h2 id="atp-token-的金鑰怎麼運作">ATP Token 的金鑰怎麼運作</h2>
<p>ATP Token 是四層結構：組織、工作區、專案、金鑰（<a href="/zh-tw/docs/console-setup/" class="doc-term-def" data-def="帳號的最上層，底下再分 工作區 與 專案。">設定組織</a>）。一把金鑰只屬於一個專案，並繼承該專案允許的模型與<a class="doc-term" href="/zh-tw/docs/credits/" data-def="計費單位。1 點＝USD 0.01；用量依各模型牌價換算成點數扣抵。">點數</a>餘額。模型權限按專案設定，從不按金鑰設定，所以同一個專案裡的兩把金鑰能呼叫的模型永遠相同。</p>
<p>建立金鑰的精靈會請你填名稱、選擇工作區與專案，並可選擇先撥入一些起始點數。金鑰以 <code>atp-</code> 開頭、長度 92 字元，完整金鑰只在建立時顯示一次，之後只看得到前綴（<a href="/zh-tw/docs/console-keys/" class="doc-term-def" data-def="以 atp- 開頭的金鑰，繼承所屬 專案 的允許模型清單與點數餘額。">管理 API 金鑰</a>）。API 金鑰頁面列出組織內所有工作區與專案的每一把金鑰，可依名稱或前綴搜尋。撤銷的金鑰立即失效，並留在清單中供稽核。</p>
<p>追查花費時，用量頁面依模型與金鑰顯示點數與 token，請求紀錄則記下每次呼叫的模型、狀態、token 數與請求 ID（<a href="/zh-tw/docs/monitoring/">用量與紀錄</a>）。請求紀錄保留 7 天，事件發生後請盡快檢查可疑的金鑰。閘道在轉發請求前會移除你的 <code>atp-</code> 金鑰，上游供應商永遠看不到它（<a href="/zh-tw/docs/how-it-works/">運作方式</a>）。</p>
<p>誰能做什麼由角色決定：Admin 管理成員、資源、金鑰與點數分配，Member 則使用自己有權限的內容（<a href="/zh-tw/docs/team/">團隊與角色</a>）。</p>

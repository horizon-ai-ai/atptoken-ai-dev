<p>先給答案：上線後帳單爆炸，十之八九不是「原廠偷偷漲價」，而是<strong>五個控制缺口</strong>在 go-live 當下同時打開。缺口可以各自修，但真正有效的是同一套順序——<strong>先讓每一塊錢有主人，再讓每一個<a class="doc-term" href="/zh-tw/docs/resources" data-def="權限與帳務的最小單位；金鑰、允許模型、點數預算都掛在 project 上。">專案</a>有天花板，最後讓每一筆請求可回放</strong>。下面逐項對照症狀、後果與修法；讀完可直接當一週內的止血清單。若要先搞懂帳單上的單位，可搭配<a href="/zh-tw/blog/how-to-read-your-ai-bill">怎麼讀懂 AI 帳單</a>。</p>
<h2 id="為什麼-go-live-是引爆點">為什麼 go-live 是引爆點</h2>
<p>試用期的流量通常短、人少、上下文乾淨。上線後三件事同時發生：</p>
<ol>
<li><strong>真實上下文變長</strong>——使用者貼整份文件、對話歷史越堆越厚。  </li>
<li><strong>呼叫形態變複雜</strong>——agent、工具呼叫、失敗重試，使「一次工作」變成「一連串請求」。  </li>
<li><strong>使用人數突然放大</strong>——從少數工程師變成整條業務線。</li>
</ol>
<p>單價表幾乎沒變，但「每次工作消耗的 token」與「誰能無上限呼叫」變了。沒有控制層的系統，會把這三件事乘在一起，反映在同一張月底總額上。公開討論裡反覆出現的失控敘事——沒有用量上限、coding agent 人均成本失控、財務答不出是哪個團隊——幾乎都能對回下面五個缺口。</p>

<h2 id="缺口一-沒有專案級金鑰-費用沒有主人">缺口一：沒有專案級金鑰——費用沒有主人</h2>
<h3 id="症狀">症狀</h3>
<p>多個服務、腳本或個人工具共用一把 API 金鑰；離職或換組時不敢輪替，因為「不知道還有誰在用」。</p>
<h3 id="為什麼上線後會炸">為什麼上線後會炸</h3>
<p>試用期流量小，共用金鑰的隱性成本被掩蓋。上線後任一子系統暴衝，你只能關掉整把金鑰——等於關掉所有人——或眼睜睜看著總額爬升。</p>
<h3 id="修法">修法</h3>
<p>把治理單位定成<strong>專案</strong>，不是「人」：一個專案一把金鑰，權限與預算掛在專案上。人離開時撤的是專案存取，不是公司共用的那把萬能鑰匙。金鑰建立時只顯示一次密文、之後可隨時撤銷並留稽核軌跡——這是<a href="/zh-tw/docs/console-keys" class="doc-term-def" data-def="以 atp- 開頭的金鑰，繼承所屬 project 的允許模型清單與點數餘額。">管理 API 金鑰</a>的基本要求，也是<a href="/zh-tw/blog/ai-governance-checklist">企業 AI 治理清單</a>的第一項。</p>
<blockquote>
<p>共用金鑰是治理裡最貴的技術債：出事時你永遠只知道「有人」，不知道「是誰」。</p>
</blockquote>
<h2 id="缺口二-沒有預算上限-爆炸沒有邊界">缺口二：沒有預算上限——爆炸沒有邊界</h2>
<h3 id="症狀-2">症狀</h3>
<p>供應商帳戶或信用卡「能刷就刷」；第一個正式訊號是 Intercom 告警、服務 402，或財務轉來的異常發票。</p>
<h3 id="為什麼上線後會炸-2">為什麼上線後會炸</h3>
<p>Agent 與批次工作可以在無人值守時連跑數小時。沒有專案天花板時，單點異常會吃掉整份組織預算——這正是公開案例裡「沒設 usage limit」反覆被點名的原因。</p>
<h3 id="修法-2">修法</h3>
<p>在<strong>專案層</strong>設可花的額度，把「分配下去的點數」當成 cap。組織 → 工作區 → 專案逐層下撥；專案只能花被分配到的量，超支應被標記並停止或降級，而不是靜默透支到公司總帳。操作順序見<a href="/zh-tw/docs/cb-budget-caps">為團隊設定預算上限</a>；點數在階層中的 Available / Allocated / Consumed 含義見<a href="/zh-tw/docs/credits" class="doc-term-def" data-def="計費單位。1 美元 = 100 點；用量依各模型牌價換算成點數扣抵。">點數如何運作</a>。</p>
<p>告警要早於切斷：Usage 上能看到 Allocated 對 Consumed 的進度，才是「上線後還活著的預算」。細節見<a href="/zh-tw/docs/spend">追蹤費用</a>。</p>
<h2 id="缺口三-沒有逐請求歸屬-月報回答不了-為什麼">缺口三：沒有逐請求歸屬——月報回答不了「為什麼」</h2>
<h3 id="症狀-3">症狀</h3>
<p>財務看到月總額上修 3 倍；工程說「我們沒改價」；沒有人能在一小時內指出是哪個模型、哪次部署。</p>
<h3 id="為什麼上線後會炸-3">為什麼上線後會炸</h3>
<p>上線後變更頻繁——提示加長、換模型、重試策略、新 agent 步數。沒有「一次請求」為最小單位的紀錄，你只能爭論意見，不能排除假設。</p>
<h3 id="修法-3">修法</h3>
<p>每一筆呼叫寫下至少：專案、金鑰、模型、輸入／輸出 token、狀態與時間。彙總才有意義；月總額是結果，不是分析起點。讀法與角色分工見<a href="/zh-tw/blog/how-to-read-your-ai-bill">怎麼讀懂 AI 帳單</a>；主控台的 Usage 與 Request logs 說明見<a href="/zh-tw/docs/monitoring">用量與紀錄</a>。</p>
<p>實用內部指標仍是<strong>每千次呼叫平均成本</strong>：它同時反映模型選擇、提示長度與快取策略，比盯著單價表更能解釋「上線後為什麼變貴」。</p>
<h2 id="缺口四-沒有模型白名單-最貴路徑成為預設">缺口四：沒有模型白名單——最貴路徑成為預設</h2>
<h3 id="症狀-4">症狀</h3>
<p>文件寫著「預設用中階模型」，實際日誌裡大量 frontier 模型；個人為了方便把 <code>model</code> 寫死成當季最強。</p>
<h3 id="為什麼上線後會炸-4">為什麼上線後會炸</h3>
<p>上線後呼叫次數放大，模型單價差會從「幾塊錢實驗」變成「預算主菜」。沒有專案級允許清單時，切換模型是一行程式碼，不是一個需要理由的決策。</p>
<h3 id="修法-4">修法</h3>
<p>在專案設定<strong>允許的模型清單</strong>；不在清單內的請求在到達任何上游之前就被拒絕（例如 403）。<code>GET /v1/models</code> 是平台菜單，不是這把金鑰的權限——這個區別寫在<a href="/zh-tw/docs/models">模型文件</a>與<a href="/zh-tw/docs/how-it-works">系統如何運作</a>。白名單讓「誰能用最貴模型」變成可回答的治理問題，而不是 code review 才能撞見的意外。</p>
<h2 id="缺口五-沒有上線後監控節奏-問題活到月底">缺口五：沒有上線後監控節奏——問題活到月底</h2>
<h3 id="症狀-5">症狀</h3>
<p>沒有人每週打開用量；異常只在發票或客戶投訴時浮現；Activity 裡的權限與額度變更無人覆核。</p>
<h3 id="為什麼上線後會炸-5">為什麼上線後會炸</h3>
<p>控制項若只在上線前檢查一次，上線後的配置漂移（新 key、放寬白名單、調高 cap）不會被看見。治理是循環，不是啟動儀式。</p>
<h3 id="修法-5">修法</h3>
<p>訂一個輕量節奏：</p>
<table>
<thead>
<tr>
<th>節奏</th>
<th>看什麼</th>
<th>誰負責</th>
</tr>
</thead>
<tbody><tr>
<td>每日（自動）</td>
<td>專案餘額與錯誤率告警</td>
<td>平台／on-call</td>
</tr>
<tr>
<td>每週</td>
<td>依專案與模型排序的消耗；異常部署對照</td>
<td>平台 + 專案負責人</td>
</tr>
<tr>
<td>每月</td>
<td>點數對帳、In debt 專案、無流量金鑰</td>
<td>財務 + 平台</td>
</tr>
<tr>
<td>每季</td>
<td>權限清理、死亡專案、白名單瘦身</td>

</tr>

<p>安全與管理事件（登入、邀請、額度變更）應與用量分開可查，見<a href="/zh-tw/docs/monitoring">用量與紀錄</a>的 Activity。完整 12 項循環見<a href="/zh-tw/blog/ai-governance-checklist">企業 AI 治理清單</a>。</p>
<h2 id="依團隊規模-一週內先補哪幾個缺口">依團隊規模：一週內先補哪幾個缺口</h2>
<h3 id="10-人以下">10 人以下</h3>
<p>先補<strong>缺口一、二、三</strong>：專案金鑰、額度上限、看得到的請求紀錄。不需要委員會，三項都是設定。</p>
<h3 id="50-到-200-人">50 到 200 人</h3>
<p>加上<strong>缺口四</strong>：跨團隊用量開始分叉，白名單決定「誰能用哪種模型」。同時把個人錢包與團隊分配分開，避免業務線刷個人卡（見<a href="/zh-tw/docs/topup" class="doc-term-def" data-def="為錢包加值點數，最低 5 美元，用多少付多少。">儲值與錢包</a>的 personal vs team 說明）。</p>
<h3 id="500-人以上">500 人以上</h3>
<p><strong>缺口五</strong>變成重心：上線只是起點，季度盤點與稽核語言（逐請求可追溯）決定預算明年還在不在。組織階層從一開始就要長對，見<a href="/zh-tw/docs/console-setup" class="doc-term-def" data-def="帳號的最上層，底下再分 workspace 與 project。">設定組織</a>。</p>
<h2 id="依使用情境-哪種工作負載最容易引爆">依使用情境：哪種工作負載最容易引爆</h2>
<h3 id="coding-agent-與內部開發助手">Coding agent 與內部開發助手</h3>
<p>長上下文、多步工具、高重試——單位工作 token 遠高於聊天。<strong>必須</strong>與生產服務拆開專案與額度；實驗額度要低到「燒光也不痛」。接入方式可參考<a href="/zh-tw/docs/cb-claude-code">在 ATP 上跑 Claude Code</a>，重點是金鑰與專案邊界，不是工具品牌。</p>
<h3 id="客服與高頻短請求">客服與高頻短請求</h3>
<p>單次便宜，次數巨大。缺口在<strong>歸屬與模型分級</strong>：把高頻路徑鎖在較小模型，frontier 留給升級路徑。</p>
<h3 id="批次與夜間-pipeline">批次與夜間 pipeline</h3>
<p>無人值守放大缺口二與五。上線前就要有 cap 與告警；失敗重試策略要有上限，否則 retry 本身就是一條隱藏成本線。</p>
<h3 id="多供應商同時導入">多供應商同時導入</h3>
<p>費率表與幣別不一致時，若沒有同一結算單位與專案歸屬，財務會先棄療。這是點數與單一帳務窗口存在的理由，不是行銷口號——見<a href="/zh-tw/docs/credits" class="doc-term-def" data-def="計費單位。1 美元 = 100 點；用量依各模型牌價換算成點數扣抵。">點數如何運作</a>。</p>
<h2 id="一週止血清單-可直接開票">一週止血清單（可直接開票）</h2>
<ol>
<li><strong>盤點</strong>：列出所有仍有效的 API 金鑰、所屬系統、是否共用。  </li>
<li><strong>切開</strong>：每個正式系統一專案一金鑰；共用 key 排程退役。  </li>
<li><strong>蓋帽</strong>：為每個專案寫下月預算並做成可執行的額度（allocate）。  </li>
<li><strong>縮權</strong>：專案白名單只留需要的模型；預設不要 frontier。  </li>
<li><strong>開燈</strong>：打開逐請求紀錄與週會上的「依專案排序消耗」報表。  </li>
<li><strong>演練</strong>：假設金鑰外洩——撤銷、追 log、重發——寫成一頁 runbook。  </li>
<li><strong>對齊名詞</strong>：讓工程與財務共用 token／點數／專案三層語言（<a href="/zh-tw/blog/how-to-read-your-ai-bill">讀懂 AI 帳單</a>）。</li>
</ol>

<h2 id="更現代的做法-把五個缺口收成系統預設">更現代的做法：把五個缺口收成系統預設</h2>
<p>五個缺口都可以靠表格、供應商後台與人工紀律暫時堵住。更現代的做法，是讓<strong>治理層與帳務整合層</strong>在預設狀態就關缺口：組織 → 工作區 → 專案的階層本身就回答「誰的預算」；專案金鑰繼承模型白名單與額度；餘額耗盡以明確狀態拒絕（例如 402），未授權模型在出站前拒絕（例如 403）；每筆請求寫入可篩選的稽核紀錄。</p>
<p>ATP Token 依這條路徑設計：相容 OpenAI、Anthropic 與 Gemini 的呼叫格式，接入通常是 base_url 與金鑰；用量以點數在階層中下撥與歸屬。它不是用來取代模型供應商，而是在導入多家 AI 服務時，把權限、用量與帳務收斂到同一平面。</p>

<h2 id="常見問題">常見問題</h2>
<h3 id="為什麼-ai-服務上線後帳單會突然暴衝">為什麼 AI 服務上線後帳單會突然暴衝？</h3>
<p>最常見的原因是 go-live 後用量形態改變——上下文變長、重試變多、agent 多步呼叫重送同一段上下文——同時又沒有專案額度上限與逐請求歸屬。單價沒變，總額卻可以在幾週內翻數倍。</p>
<h3 id="企業-ai-預算上限應該設在哪一層">企業 AI 預算上限應該設在哪一層？</h3>
<p>應該設在專案（或等同於專案的工作負載）這一層，而不是只設在整公司一張信用卡。專案層上限能隔離爆炸範圍；公司總額只能告訴你「爆了」，說不出「哪裡爆了」。</p>
<h3 id="共用一把-api-金鑰為什麼會讓帳單失控">共用一把 API 金鑰為什麼會讓帳單失控？</h3>
<p>共用金鑰讓每筆請求失去主人。出事時你只知道「有人」在燒錢，無法依專案停掉、限流或追溯。歸帳與止血都從「一專案一金鑰」開始。</p>
<h3 id="沒有治理平台能不能先堵住這些缺口">沒有治理平台能不能先堵住這些缺口？</h3>
<p>可以。先用表格盤點金鑰與專案、在供應商後台設額度告警、強制模型白名單、把請求日誌匯出到現有監控。平台的價值是把這些步驟變成預設值，而不是唯一做法。</p>
<h3 id="coding-agent-和一般聊天-api-的帳單風險有何不同">coding agent 和一般聊天 API 的帳單風險有何不同？</h3>
<p>Coding agent 常在長上下文、多輪工具呼叫與重試下運行，單位工作的 token 消耗遠高於單次問答。若與生產服務共用金鑰與額度，實驗流量很容易把正式預算吃光。</p>

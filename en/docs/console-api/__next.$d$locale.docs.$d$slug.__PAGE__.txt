<h2 data-md="h2" id="authentication" class="group">Authentication<a href="#authentication" aria-label="Link to this section" class="ml-2 text-sand opacity-0 group-hover:opacity-100 focus-visible:opacity-100 touch:opacity-60">#</a></h2>4:Tb37,<h3 data-md="h3" id="a-person-has-to-sign-in" class="group">A person has to sign in<a href="#a-person-has-to-sign-in" aria-label="Link to this section" class="ml-2 text-sand opacity-0 group-hover:opacity-100 focus-visible:opacity-100 touch:opacity-60">#</a></h3>
<p><code>POST /api/users/login</code> requires a human-verification answer in its body, and only a browser can produce one. There is no API key, no service account and no machine sign-in for the Console API: every call on these pages is made with the session token of a person who signed in at <a href="https://atptoken.ai" target="_blank" rel="noopener noreferrer">atptoken.ai</a>.</p>
<p>That is a decision, not a gap waiting to be filled. Sign-in is the surface password-guessing scripts attack, and the per-account attempt limit that used to be the only brake punished the wrong party — the script moved on to the next account while the real holder sat locked out of their own. A human check stops that run at its first request, so it applies to every sign-in, with no threshold to cross and no exemption to earn.</p>
<p>Sign in in your browser, and the console holds that session token in <code>localStorage</code> under <code>atp_token</code> — it is the <code>$TOKEN</code> in the examples below. The token is a Bearer token valid for roughly <strong>2 hours</strong>, and <code>POST /api/users/logout</code> ends it early.</p>
<h3 data-md="h3" id="what-that-rules-out" class="group">What that rules out<a href="#what-that-rules-out" aria-label="Link to this section" class="ml-2 text-sand opacity-0 group-hover:opacity-100 focus-visible:opacity-100 touch:opacity-60">#</a></h3>
<p>A script cannot sign itself in, so it cannot keep itself authenticated: once the token expires, a person signs in again. Use the Console API for work you run with a session in hand — a report, a reconciliation, chasing down a failed request — not as an unattended service.</p>
<p>For a spending limit that needs no session at all, allocate <a class="doc-term" href="/docs/credits/" data-def="The billing unit. 1 USD = 100 credits; usage converts at each model's list rate.">credits</a> instead of watching them: a project can only spend what was allocated to it, and the Gateway enforces that on every request. See <a href="/docs/cb-budget-caps/">Set up a team with budget caps</a>.</p>

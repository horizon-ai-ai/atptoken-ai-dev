3:T439,<p>Image generation is <strong>asynchronous</strong> — there is no synchronous version. It takes three steps: create a task (<code>202</code> + an <code>img_…</code> task id), poll until the status is terminal, then download <code>data[].url</code> within 24 hours. Point your client at the media base URL <code>https://api.atptoken.ai/omni/media/v1</code> and authenticate with a <a class="doc-term" href="/docs/resources/" data-def="The unit that permissions and billing hang off — keys, allowed models, and credit budget all belong to one.">project</a> <code>atp-</code> key. The flow matches video generation.</p>
<ul>
<li><strong>Output is a signed URL (<code>https://media-&lt;env&gt;.atptoken.ai/v/...</code>) valid for 24 hours</strong> — never inline base64. Download it if you need to keep it; don&#39;t store the URL as a permanent link.</li>
<li>Requests are refused with <code>402 insufficient_quota</code> when the project balance is ≤ 0.</li>
<li><code>callback_url</code> is accepted but <strong>no webhook is ever sent</strong>. You must poll.</li>
</ul>4:T4de,<p>Sending only <code>image</code> without <code>face_image</code> does not waive <code>prompt</code> — you get &quot;prompt is required&quot;.</p>

<p>Same endpoint, same flow — but <strong>each model family puts the input image in a different place</strong>:</p>5:T76b,<ul>
<li><strong>Exit the loop on all four terminal statuses.</strong> A loop that waits only for <code>succeeded</code> spins forever on <code>failed</code>.</li>
<li><strong><code>succeeded</code> does not guarantee a file.</strong> After 24 hours the status is still <code>succeeded</code>, but <code>data[].url</code> becomes <code>null</code> and <code>expired: true</code> appears. After checking <code>succeeded</code>, check that the URL is not <code>null</code>. The only way to get it back is to generate again.</li>
<li><code>data</code> is an array — one URL per image when you generate several. Walk the whole array to get them all.</li>
<li><code>usage</code> reports token usage; <code>meters</code> says what the task was actually metered on (per-image models have no tokens — read <code>meters</code>).</li>
<li>A <code>failed</code> task carries an <code>error</code> object (<code>code</code>, <code>message</code>, plus <code>upstream_status</code> when the failure had an HTTP status).</li>
<li><strong>Parameter-value errors may only show up when polling.</strong> For the <code>nano-banana</code> family, <code>gpt-image-2</code> and the <code>qwen-image</code> family, create checks only the request shape; an invalid value surfaces as <code>failed</code> on poll — e.g. an out-of-range qwen-image size gives <code>{&quot;code&quot;:&quot;upstream_400&quot;,&quot;upstream_status&quot;:400,&quot;message&quot;:&quot;Image area must be between …&quot;}</code>. The <code>kling-*</code> family instead returns errors at create, with the status code passed through unchanged.</li>
<li><strong>The extension in <code>data[].url</code> is not a format signal</strong>: a URL ending <code>.png</code> can carry JPEG bytes. If the format matters downstream (re-uploading the result, converting it), sniff the bytes (magic number) instead of trusting the filename.</li>

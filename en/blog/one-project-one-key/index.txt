28:T25b1,<p>API key management for LLM APIs is the set of rules for who gets a key, what each key can reach, where it is stored, and how it is rotated and revoked. The pattern that holds up in production is one <a class="doc-term" href="/docs/resources/" data-def="The unit that permissions and billing hang off — keys, allowed models, and credit budget all belong to one.">project</a>, one key: each workload gets its own project, and that project&#39;s key carries its own model list and budget. Below are three ways a shared key fails, an issuance pattern, a table of where the key lives in each environment, and a 30-day migration runbook.</p>
<h2 id="three-ways-a-shared-key-goes-wrong">Three ways a shared key goes wrong</h2>
<h3 id="the-offboarded-contractor">The offboarded contractor</h3>
<p>A contractor builds the retrieval prototype with the company&#39;s only API key in a local <code>.env</code> file, then leaves on a Friday. The same key also runs the support bot, the nightly summarization job and an internal Slack assistant. Revoking it that afternoon breaks all three. Leaving it means a former contractor still holds a working key. Most teams choose &quot;rotate next sprint&quot;, and the sprint fills up.</p>
<p>With one key per project, the contractor only ever had the key for their sandbox project. You revoke it and nothing else changes.</p>
<h3 id="the-key-in-a-public-repo">The key in a public repo</h3>
<p>Someone commits a config file with the key to a public repository. Whoever finds it can send traffic that lands on your bill, and because every service sends the same credential, their requests look exactly like yours in the usage data. The fix is the same as the contractor case, with the same outage attached.</p>
<h3 id="the-spike-nobody-can-attribute">The spike nobody can attribute</h3>
<p>The monthly bill doubles. The provider dashboard shows which model grew, but every request carries the same key, so nobody can say which product caused it. Finance asks for a breakdown by product; engineering spends two days matching timestamps across service logs.</p>
<h2 id="what-the-vendors-recommend">What the vendors recommend</h2>
<p>OpenAI&#39;s <a href="https://help.openai.com/en/articles/5112595-best-practices-for-api-key-safety" target="_blank" rel="noopener noreferrer">best practices for API key safety</a> ask for a unique API key per team member, rotation and expiry, and never putting keys in client-side code. OpenAI also recommends separate projects for staging and production, each with its own limits (<a href="https://developers.openai.com/api/docs/guides/production-best-practices" target="_blank" rel="noopener noreferrer">production best practices</a>). Anthropic lets you scope an API key to a single Console <a href="https://platform.claude.com/docs/en/manage-claude/workspaces" target="_blank" rel="noopener noreferrer">workspace</a>. Vercel AI Gateway keys can carry a budget and an expiry, which suits a contractor key with a fixed end date (<a href="https://vercel.com/docs/ai-gateway/observability-and-spend/budgets" target="_blank" rel="noopener noreferrer">Vercel budgets</a>).</p>
<p>Per-person keys solve offboarding for humans. A production service should not run on a person&#39;s key, because removing that person then stops the service. The working split is personal keys for personal sandboxes and a project key for each deployed workload.</p>
<h2 id="the-issuance-pattern">The issuance pattern</h2>
<ol>
<li><strong>One project per workload and environment.</strong> <code>support-bot-prod</code> and <code>support-bot-staging</code> are separate projects with separate keys.</li>
<li>One key per project for services. People who experiment get their own sandbox project.</li>
<li>Name keys after service, environment and month of issue, for example <code>support-bot-prod-2026-10</code>, so a key found in a log or a repo points to its owner.</li>
<li>Move the secret straight from the console into the secret manager. Never paste it into chat, tickets or docs.</li>
<li>Rotate by overlap: issue a new key in the same project, deploy it, confirm traffic has moved, then revoke the old one.</li>
</ol>

<h2 id="how-atp-token-keys-work">How ATP Token keys work</h2>
<p>ATP Token has a four-level tree: organization, workspace, project and key (<a href="/docs/console-setup/" class="doc-term-def" data-def="The top level of an account. Workspaces and projects sit underneath it.">set up your organization</a>). A key belongs to exactly one project and inherits that project&#39;s allowed models and credit balance. Model access is set per project, never per key, so two keys in the same project can always call the same models.</p>
<p>The Create key wizard asks for a name, the workspace and project, and optionally some starting <a class="doc-term" href="/docs/credits/" data-def="The billing unit. 1 USD = 100 credits; usage converts at each model's list rate.">credits</a>. Keys start with <code>atp-</code>, are 92 characters long, and the full secret is displayed once; afterwards only the prefix is visible (<a href="/docs/console-keys/" class="doc-term-def" data-def="A key that starts with atp-. It inherits its project's allowed models and credit balance.">managing API keys</a>). The API keys page lists every key in the organization across all workspaces and projects, searchable by name or prefix. A revoked key stops working immediately and stays in the roster for audit.</p>
<p>For attribution, the Usage page shows credits and tokens by model and by key, and request logs record each call with its model, status, token counts and request ID (<a href="/docs/monitoring/">usage and logs</a>). Request logs are kept for 7 days, so review a suspect key soon after an incident. The gateway strips your <code>atp-</code> key before forwarding a request, so upstream providers never see it (<a href="/docs/how-it-works/">how it works</a>).</p>
<p>Who can do what is set by role: an Admin manages members, resources, keys and credit allocation, and a Member uses what they have access to (<a href="/docs/team/">team and roles</a>).</p>

27:T1a53,<p>One <a class="doc-term" href="/en/docs/resources" data-def="The unit that permissions and billing hang off — keys, allowed models, and credit budget all belong to one.">project</a>, one key is the rule that each AI workload uses a project-scoped API key that inherits that project&#39;s model allowlist and budget—so spend, access, and revocation all have a single owner. This guide is for platform and security teams still running production traffic on a shared vendor key.</p>
<p>The conclusion first: <strong>shared keys optimize for speed on day one and maximize blast radius on day one hundred.</strong> Attribution, caps, and incident response all require project-scoped credentials. This is item one of the <a href="/en/blog/ai-governance-checklist">enterprise AI governance checklist</a> and the root of several <a href="/en/blog/why-ai-bills-explode-after-go-live">post-go-live control gaps</a>.</p>

<p>When the bill jumps, <a href="/en/docs/monitoring">request logs</a> that only know one key can say which model was hot—not which team.</p>
<h2 id="what-one-project-one-key-requires">What “one project, one key” requires</h2>
<p>From <a href="/en/docs/console-setup" class="doc-term-def" data-def="The top level of an account. Workspaces and projects sit underneath it.">set up your organization</a> and <a href="/en/docs/console-keys" class="doc-term-def" data-def="A key that starts with atp-. It inherits its project's allowed models and credit balance.">managing API keys</a>:</p>
<ol>
<li><strong>Organization</strong> — billing and team boundary  </li>
<li><strong>Workspace</strong> — credit container for related work  </li>
<li><strong>Project</strong> — allowed models + credit balance  </li>
<li><strong>API key</strong> — scoped to exactly one project</li>
</ol>
<p>The secret is shown once (<code>atp-</code> prefix on ATP), stored outside git, revocable immediately, retained in the roster for audit.</p>
<h2 id="by-environment">By environment</h2>
<h3 id="production">Production</h3>
<p>One key per deployable service. Never share with local laptops.</p>
<h3 id="staging">Staging</h3>
<p>Separate project and low cap. Staging bugs should not drain production allocation (<a href="/en/docs/cb-budget-caps">budget caps</a>).</p>
<h3 id="experiments-and-coding-agents">Experiments and coding agents</h3>
<p>Disposable projects, cheap models on the allowlist, caps low enough to burn. See <a href="/en/blog/what-is-the-agent-tax">agent tax</a> and <a href="/en/docs/cb-claude-code">Claude Code on ATP</a>.</p>
<h2 id="by-team-size">By team size</h2>
<p>Small teams: three projects—prod, staging, sandbox—are enough.<br>Mid-size: one project per product surface.<br>Enterprise: align projects to cost centers; roles at workspace/project (<a href="/en/docs/team">team</a>).</p>
<h2 id="migration-plan-off-a-skeleton-key">Migration plan off a skeleton key</h2>
<ol>
<li>Inventory every caller of the shared secret.  </li>
<li>Create projects and issue keys (<a href="/en/docs/console-keys" class="doc-term-def" data-def="A key that starts with atp-. It inherits its project's allowed models and credit balance.">console keys</a>).  </li>
<li>Dual-run with tight <a href="/en/docs/credits" class="doc-term-def" data-def="The billing unit. 1 USD = 100 credits; usage converts at each model's list rate.">allocations</a>.  </li>
<li>Cut over service by service.  </li>
<li>Revoke the shared key; confirm zero traffic in <a href="/en/docs/monitoring">logs</a>.  </li>
<li>Document the incident path: revoke → trace → reissue.</li>
</ol>
<h2 id="a-more-modern-approach">A more modern approach</h2>
<p>Policy PDFs that say “do not share keys” lose to convenience. Platforms that <strong>cannot issue non-project keys</strong> make the right path the easy path. ATP Token binds every key to a project’s models and credits; revoked keys stay visible for audit. Wire formats stay OpenAI / Anthropic / Gemini-compatible—migration is usually base_url and key (<a href="/en/docs/cb-migrate-openai">migrate from OpenAI</a>).</p>

<h2 id="faqs">FAQs</h2>
<h3 id="what-does-one-project-one-key-mean">What does one project, one key mean?</h3>
<p>It means every production workload gets its own project-scoped API key that inherits that project&#39;s allowed models and credit balance, so every request has a clear owner for spend and access.</p>
<h3 id="why-are-shared-api-keys-risky-for-ai-usage">Why are shared API keys risky for AI usage?</h3>
<p>Shared keys hide which system spent tokens, block safe revocation on offboarding, and turn any leak into an organization-wide incident instead of a project-scoped blast radius.</p>
<h3 id="how-should-enterprises-issue-llm-api-keys">How should enterprises issue LLM API keys?</h3>
<p>Create a project per system or product surface, enable only needed models, allocate a budget, issue a key shown once, store it in a secret manager, and revoke from the console when the project ends.</p>
<h3 id="what-happens-when-someone-leaves-if-keys-follow-projects">What happens when someone leaves if keys follow projects?</h3>
<p>You remove their membership or project access; you do not rotate a single key that half the company depends on. Project keys stay with the workload, not the person.</p>
<h3 id="how-do-i-migrate-off-a-shared-ai-key">How do I migrate off a shared AI key?</h3>
<p>Inventory callers, create project keys per system, dual-run with low caps, cut traffic system by system, then revoke the shared key and keep it in the audit roster.</p>

a:T12c9,<p>A model catalog is the list of model ids a platform can serve; model access control is the policy that decides which of those ids a given project key may call. This guide is for engineers who treat “it appears in <code>/v1/models</code>” as “we are allowed to use it.”</p>
<p><strong>Menu ≠ permission.</strong> On ATP, list endpoints describe the platform; project allowlists enforce access and return 403 when violated (<a href="/en/docs/models">models</a>, <a href="/en/docs/how-it-works">how it works</a>). Confusing the two is a quiet driver of <a href="/en/blog/why-ai-bills-explode-after-go-live">post-go-live bill spikes</a>.</p>

<h2 id="why-catalogs-look-like-permission">Why catalogs look like permission</h2>
<p>SDKs print friendly model lists. Marketplaces celebrate breadth. Without a gateway check, any string in <code>model=</code> is a purchase order. Governance platforms separate discovery from authorization so finance and security can answer “who may use Opus-class models.”</p>
<h2 id="designing-allowlists">Designing allowlists</h2>
<ol>
<li><strong>Default deny</strong> for frontier ids.  </li>
<li><strong>Per project</strong>, not per human (<a href="/en/blog/one-project-one-key">one project, one key</a>).  </li>
<li><strong>Change control</strong> — widening allowlist is a logged admin event (<a href="/en/docs/monitoring">monitoring</a>).  </li>
<li><strong>Pair with caps</strong> (<a href="/en/blog/ai-spending-caps-that-work">spending caps</a>).  </li>
<li><strong>Document for app teams</strong> — 403 means policy, not outage (<a href="/en/docs/errors">errors</a>).</li>
</ol>
<h2 id="by-use-case">By use case</h2>
<p><strong>Customer-facing bots:</strong> small stable set.<br><strong>Internal agents:</strong> mid-tier + optional frontier project.<br><strong>Eval sandboxes:</strong> wider list, tiny allocation.</p>
<h2 id="a-more-modern-approach">A more modern approach</h2>
<p>Spreadsheets of “approved models” rot. Runtime allowlists on the project do not. ATP Token sets allowed models per project; every key inherits them; unauthorized calls never reach providers.</p>

<h2 id="faqs">FAQs</h2>
<h3 id="what-is-the-difference-between-a-model-catalog-and-model-access-control">What is the difference between a model catalog and model access control?</h3>
<p>A catalog lists models a platform can route. Access control is the per-project (or per-key) policy that allows or denies those models at request time.</p>
<h3 id="why-does-my-api-return-403-for-a-model-i-see-in-the-docs">Why does my API return 403 for a model I see in the docs?</h3>
<p>Documentation and list endpoints often show the platform menu. If the model is not on your project allowlist, a governance gateway rejects the call before upstream.</p>
<h3 id="should-every-project-allow-frontier-models">Should every project allow frontier models?</h3>
<p>No. Default mid-tier models for high-volume paths; enable frontier models only for projects with budget and a written reason.</p>
<h3 id="how-do-model-allowlists-reduce-ai-cost">How do model allowlists reduce AI cost?</h3>
<p>They prevent silent upgrades to expensive models in application code. Cost control still needs spending caps; allowlists remove accidental premium routing.</p>
<h3 id="where-should-model-policy-live-code-or-platform">Where should model policy live—code or platform?</h3>
<p>Platform enforcement survives client bugs and forks. Code can default wisely; the gateway must be the final authority.</p>
